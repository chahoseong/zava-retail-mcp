# 보안 및 멀티 테넌시 (Security and Multi-Tenancy)

앨리스(Alice)는 매장 A를 관리합니다. 그녀는 성공적으로 로그인한 후 매출 도구에 매장 B의 매출을 요청합니다. 매장 B는 실제로 존재하고, 앨리스의 토큰은 유효하며, 쿼리도 정상적으로 실행될 수 있는 상태입니다. 하지만 이 요청은 반드시 거부되어야 합니다. 인증(Authentication)은 호출자가 누구인지를 확인했을 뿐, 해당 매장의 데이터를 읽을 수 있는 권한(Permission)까지 확인한 것은 아니기 때문입니다.

이제 앨리스의 요청이 끝나고 데이터베이스 커넥션이 풀(Pool)로 반환되었다고 가정해 보겠습니다. 다른 매장을 조회하는 요청이 바로 그 동일한 커넥션을 대여(Borrow)합니다. 만약 이전 매장의 스코프(Scope)가 커넥션에 남아 있다면, 올바르게 인증된 요청이라 할지라도 엉뚱한 데이터에 접근할 수 있게 됩니다. 보안은 단순히 로그인 화면이나 데이터베이스 정책의 존재 여부뿐만 아니라, 이 단계들 사이에서 내려지는 결정에 달려 있습니다.

본 실습에서는 자바 리테일(Zava Retail)을 위한 이러한 결정 사항들을 설명합니다. 인증, 인가(Authorization), 테넌트 격리(Tenant Isolation), 감사(Auditing), 유효성 검증의 기반이 되는 원칙들을 다룹니다. 구체적인 구현은 이후 실습에서 이어집니다.

## 학습 목표 (What You Will Learn)

본 실습을 완료하면 다음을 수행할 수 있게 됩니다:

- 테넌트의 범위와 보호해야 할 데이터·자원을 파악하고, 신뢰 경계(Trust Boundary)가 어디에 있는지 설명합니다.
- 호출자의 신원을 확인하는 **인증**과 작업·데이터 접근 권한을 판단하는 **인가**를 구분합니다.
- 작업 권한, 매장별 접근 권한, PostgreSQL 행 수준 보안(RLS)이 각각 무엇을 통제하는지 설명합니다.
- 커넥션을 재사용할 때 이전 요청의 매장 접근 범위가 다음 요청에 적용되지 않도록 하는 원리를 설명합니다.
- 감사 기록에 어떤 정보를 남기고, 그 기록을 어떻게 보호할지 판단합니다.
- 권한이 있는 요청은 허용되고 권한이 없는 요청은 거부되는지 확인할 검증 시나리오를 작성합니다.

먼저 [실습 01: 핵심 아키텍처](../01-Architecture/README.md)를 읽어보시기 바랍니다. 해당 실습에서 다룬 프로토콜, 비즈니스, 데이터 접근, 인프라 계층이 본 애플리케이션의 기본 구조로 유지됩니다. 여기서 다루는 보안 통제 장치는 이러한 계층 전반에 걸쳐 작동합니다. 본 문서의 HTTP 인가 참조는 본 과정의 MCP `2026-07-28` 프로필을 대상으로 하며, 데이터베이스 참조는 PostgreSQL 18을 기준으로 합니다. 이후 실습의 구현 예제는 이러한 선택 사항 및 [소개](../00-Introduction/README.md)에서 선택한 기술 스택에 맞춰 계속 업데이트될 수 있습니다.

## 멀티 테넌트 보안 아키텍처 (Multi-Tenant Security Architecture)

### 멀티 테넌시 모델 (Multi-Tenancy Models)

**테넌트(Tenant)는 서비스를 이용하는 고객, 조직 또는 사용자 집단을 구분하는 논리적 단위입니다.** 예를 들어 여러 회사가 사용하는 회계 서비스에서는 각 회사를 하나의 테넌트로 볼 수 있습니다. 한 회사의 직원 여러 명이 같은 테넌트에 속하므로, 테넌트와 개별 사용자는 서로 다른 개념입니다.

여러 테넌트가 하나의 서비스를 이용하는 구성을 **멀티테넌시(Multi-Tenancy)**라고 합니다. 서버나 데이터베이스를 공유할 수 있지만, 각 테넌트의 비공개 데이터에 대한 접근은 권한에 따라 제한해야 합니다. 서비스를 함께 사용한다는 것이 서로의 데이터를 자유롭게 볼 수 있다는 뜻은 아닙니다.

이 실습에서는 **매장(Store)을 테넌트로 모델링합니다.** 매장 A와 매장 B는 같은 MCP 서비스를 이용하지만, 매장 A를 관리하는 앨리스에게 매장 B의 매출 조회 권한이 자동으로 주어지지는 않습니다. 여러 매장을 담당하는 관리자에게는 별도의 권한을 부여할 수 있습니다. 따라서 매장별 비공개 고객 정보, 거래 내역, 재고 등은 저장·조회되는 위치와 관계없이 해당 매장의 접근 정책을 따라야 합니다.

본 실습에서는 공유 데이터베이스, 공유 스키마(Shared Database, Shared Schema) 모델을 사용합니다. 매장들은 테이블과 인프라를 공유하며, 소유권 키와 행 정책을 통해 데이터를 구분합니다. 이 방식은 운영해야 하는 데이터베이스 및 마이그레이션 수를 줄여줍니다. 동시에 정책 적용 범위, 커넥션 상태, 테넌트 인식 복구, 공유 자원 제한을 설계의 중요한 요소로 만들어 줍니다.

| 모델 | 분리 경계 (Separation boundary) | 운영상의 결과 (Operational consequence) |
| :--- | :--- | :--- |
| **공유 데이터베이스, 공유 스키마**<br>(Shared database, shared schema) | 공통 테이블 내의 매장 소유권 및 접근 정책 | 운영할 데이터베이스 객체 수가 적지만, 세심한 정책 및 상태 관리가 필요함. |
| **공유 데이터베이스, 개별 스키마**<br>(Shared database, separate schemas) | 단일 데이터베이스 내의 테넌트별 네임스페이스 | 스키마 마이그레이션 및 권한 관리가 증가하며, 데이터베이스 자원은 여전히 공유됨. |
| **개별 데이터베이스**<br>(Separate databases) | 테넌트 데이터 및 권한에 대한 물리적 데이터베이스 경계 | 프로비저닝 및 복구 작업이 증가하지만, 테넌트별 관리에 대한 유연성이 향상됨. |

이러한 모델들은 서로 다른 트레이드오프를 가집니다. 개별 데이터베이스를 사용한다고 해서 애플리케이션이나 관리자의 실수가 완전히 사라지는 것은 아니며, 공유 스키마를 쓴다고 해서 격리가 자동으로 이루어지는 것도 아닙니다. 모든 모델은 올바른 권한 할당과 애플리케이션 인가를 필요로 합니다. 특정 구성을 만능 보안 보증으로 취급하기보다는, 요구되는 신뢰 경계, 복구 요구사항 및 운영 역량에 맞춰 모델을 선택해야 합니다.

### 보안 계층 개요 (Security Layers Overview)

보안 통제는 들어오는 요청과 저장된 데이터 사이의 여러 지점에서 작동합니다. 각 지점은 서로 다른 질문에 답합니다. 즉, 이 트래픽이 서버에 도달해야 하는가? 이 호출자가 작업을 수행할 수 있는가? 그리고 그 작업이 어떤 행에 접근할 수 있는가?

다음 다이어그램은 이러한 책임들이 어디에 속하는지 보여줍니다. 상자들은 통제 장치가 위치하는 지점을 나타낼 뿐이며, 모든 상자가 별도의 신뢰 경계이거나 독립적으로 배포되는 서비스임을 의미하지는 않습니다. 애플리케이션 계층은 실습 01에서 소개된 구조를 그대로 따릅니다.

```text
┌──────────────────────────────────────────────────────────┐
│                  [HTTP Entry and Edge]                   │
│         TLS · Traffic filtering · Request limits         │
└───────────────────────────┬──────────────────────────────┘
                            ▼
┌──────────────────────────────────────────────────────────┐
│                       [MCP Server]                       │
│                                                          │
│  [Protocol Layer]     Credential and request validation  │
│           ↓                                              │
│  [Business Logic]     Authorization                      │
│           ↓                                              │
│  [Data Access]        Controlled queries and RLS context │
│                                                          │
│  [Infrastructure support]                                │
│  Connection pools · Timeouts · Credential management     │
└───────────────────────────┬──────────────────────────────┘
                            ▼
┌──────────────────────────────────────────────────────────┐
│                       [PostgreSQL]                       │
│             Restricted privileges · RLS policies         │
└──────────────────────────────────────────────────────────┘
```

HTTP 진입점에서는 TLS가 통신을 보호합니다. 배포 환경에 따라 리버스 프록시, 게이트웨이 또는 엣지 서비스가 트래픽을 필터링하고 요청 제한을 강제할 수도 있습니다.

MCP 서버 내부에서는 프로토콜 계층이 자격 증명과 요청 구조를 검증합니다. 비즈니스 계층은 호출자가 선택된 매장의 데이터에 대해 요청된 작업을 수행할 수 있는지 검사합니다. 이는 서로 분리된 검사입니다. 유효한 자격 증명이 있다고 해서 모든 도구나 매장에 대한 접근 권한이 부여되는 것은 아닙니다.

데이터 접근 계층은 비즈니스 결정을 제어된 데이터베이스 작업으로 변환합니다. 파라미터화된 쿼리를 사용하여 값을 바인딩하고, 동적 쿼리 구조를 엄격히 제한하며, 인가 결과에 따라 매장 ID를 사용자 정의 설정값에 저장합니다. 이 설정값은 해당 트랜잭션에서만 적용되도록 구성합니다. PostgreSQL은 데이터베이스 권한과 RLS 정책을 결합하여 접근 가능한 행을 제한합니다. 이를 위해서는 의도된 정책을 우회할 수 없는 제한된 런타임 역할이 필요합니다.

커넥션 관리는 또 다른 인가 단계를 구성하기보다는 이러한 경로를 지원하는 역할을 합니다. 커넥션 풀을 통해 커넥션을 재사용할 수 있으며, 타임아웃과 동시성 제한을 통해 리소스 사용량을 제한합니다. 커넥션 재사용은 격리 위험을 수반하기도 합니다. 이후의 요청이 이전 요청에서 설정한 매장 ID를 그대로 사용해서는 안 됩니다.

감사 로깅(Audit Logging)은 이러한 위치 전반에 걸쳐 이루어집니다. 게이트웨이는 거부된 트래픽을 기록하고, 서버는 거부된 작업을 기록하며, 데이터베이스는 데이터 변경 사항을 기록할 수 있습니다. 데이터베이스 트리거만으로는 쿼리가 PostgreSQL에 도달하기 전에 거부된 요청을 캡처할 수 없습니다. 이러한 감사 기록은 안전하게 취급되어야 하며, 시스템 전반에 걸쳐 작업을 추적 및 조사할 수 있는 충분한 상관관계 정보(Correlation Information)를 포함해야 합니다.

### 신뢰 경계 (Trust Boundaries)

소프트웨어 계층은 책임을 분리합니다. 신뢰 경계는 정보가 권한을 갖기 전에 반드시 검증되어야 하는 지점을 의미합니다. 두 개념은 일치할 수도 있지만 서로 대체될 수는 없습니다.

매장 B의 주문을 읽으라는 요청을 생각해 보겠습니다:

- **클라이언트에서 서버로**: 자격 증명과 도구 인자는 신뢰할 수 없는 입력(Untrusted Input)으로 도착합니다. 서버는 자격 증명의 클레임을 신뢰하기 전에 이를 먼저 검증합니다. 클라이언트가 제공한 매장 ID는 요청된 범위일 뿐, 접근 권한의 증거가 될 수 없습니다.
- **신원에서 인가된 작업으로**: 비즈니스 정책은 해당 호출자가 매장 B의 주문을 읽을 수 있는지 검사합니다. 인증되었거나 매장 A에 대한 접근 권한이 있다고 해서 그 질문에 답이 되는 것은 아닙니다.
- **애플리케이션에서 데이터베이스로**: 데이터 접근 계층은 인가 결과에 따라 매장 ID를 트랜잭션 범위의 사용자 정의 설정값으로 전달하고, PostgreSQL은 구성된 권한과 행 정책을 강제합니다. 전달한 매장 ID는 이번 조회의 대상을 나타낼 뿐이며, 호출자의 접근 권한을 독립적으로 증명하지는 않습니다.

이러한 통제 장치들은 상호 보완적으로 작동합니다. 트래픽 필터링은 매장 접근 권한을 결정할 수 없고, 입력 검증은 인가를 대체할 수 없으며, 이 설계의 RLS는 잘못된 매장 ID를 설정값으로 전달하는 애플리케이션의 오류를 교정해 줄 수 없습니다.

반환되는 행 데이터 외의 자산도 보호해야 합니다. 보고서, 결과 건수, 비공개 임베딩, 캐시된 응답, 오류 메시지 및 감사 기록 모두 테넌트 데이터를 노출할 수 있습니다. 가용성 또한 중요합니다. 특정 매장의 비용이 많이 드는 검색 작업이 다른 모든 매장의 공유 추론이나 데이터베이스 용량을 고갈시켜서는 안 됩니다.

## 인증: 호출자의 신원 확인

### 호출자의 신원을 확인해야 하는 이유

앨리스가 매출 조회를 요청하면서 자신의 이름과 매장 A의 관리자라는 설명을 함께 보냈다고 가정해 보겠습니다. 서버가 그 설명만 믿는다면 다른 사람도 앨리스의 이름을 적어 같은 요청을 보낼 수 있습니다. 요청에 사용자 이름이 들어 있다는 사실과 그 요청을 보낸 사람의 신원이 확인되었다는 사실은 다릅니다.

인증(Authentication)은 정해진 방식으로 호출자의 신원을 확인하는 과정입니다. 서버에는 호출자가 스스로 작성한 설명 외에 신원을 확인할 근거가 필요합니다. AI 모델이 사용자를 관리자라고 소개하거나 도구 인자에 사용자 이름을 넣는 것만으로는 이러한 확인이 이루어지지 않습니다.

### 로그인부터 토큰 검증까지

자격 증명(Credential)은 신원 확인이나 접근 요청을 검증할 때 제시하는 정보입니다. 이 실습에서는 인증이 필요한 HTTP 서버를 예로 들며, 클라이언트는 **액세스 토큰(Access Token)**을 제시합니다. 액세스 토큰은 보호된 API에 접근할 때 사용하는 문자열이며, 서버가 신뢰하는 서비스에서 발급받습니다. [액세스 토큰의 표준 정의][oauth-access-tokens]를 참고할 수 있습니다.

앨리스의 요청은 다음 흐름을 거칩니다.

1. **로그인과 토큰 발급:** 앨리스는 로그인과 토큰 발급을 담당하는 서비스를 이용합니다. 그 서비스는 로그인 과정에서 사용자를 확인하고, 클라이언트가 MCP 서버에 제시할 토큰을 발급합니다.
2. **요청에 토큰 제시:** MCP 클라이언트는 토큰을 MCP 서버에 보내는 요청과 함께 전달합니다. 앨리스라는 이름을 적는 것 외에, 서버가 검증할 수 있는 자격 증명을 제시하는 것입니다.
3. **서버의 검증:** MCP 서버는 제시된 토큰이 자신의 검증 조건을 충족하는지 확인합니다. 이 예제에서는 검증 결과에서 확인한 호출자 정보를 이후의 권한 판단에 사용합니다.

이 흐름에서 로그인 서비스는 사용자를 확인하고 토큰을 발급하며, MCP 서버는 그 토큰을 검증하는 역할을 맡습니다. 클라이언트가 로그인을 마쳤다는 사실만으로 MCP 서버의 검증이 끝나는 것은 아닙니다. 서버는 자신에게 도착한 요청의 자격 증명을 확인해야 합니다.

### 토큰을 검증해야 하는 이유

일부 토큰에는 사용자 식별자나 유효 기간 같은 정보가 들어 있습니다. 이런 정보 항목을 **클레임(Claim)**이라고 합니다. 토큰에서 앨리스라는 정보를 읽을 수 있더라도, 누군가 임의로 작성하거나 변경한 내용일 수 있습니다. 따라서 내용을 읽는 것과 그 내용을 신뢰할 수 있는지 검증하는 것을 구분해야 합니다.

검증이 필요한 이유는 다음 네 가지 질문으로 이해할 수 있습니다.

- **신뢰하는 곳에서 발급했는가?** 토큰을 발급했다는 곳이 서버가 신뢰하도록 정한 서비스인지 확인합니다. 모르는 곳에서 발급한 토큰에 앨리스의 이름이 적혀 있다고 해서 그 신원을 받아들일 수는 없습니다.
- **내용이 변조되지 않았는가?** 누군가 사용자 식별자나 유효 기간을 바꾼 토큰을 정상적인 자격 증명으로 받아들여서는 안 됩니다. 서명된 토큰은 서명 검증을 통해 이러한 변경 여부를 확인합니다.
- **이 서버에 사용할 수 있는가?** 앨리스가 다른 API를 위해 발급받은 유효한 토큰을 가지고 있어도, 그것이 MCP 서버에 접근할 자격 증명이 되지는 않습니다. 토큰이 사용될 대상으로 이 서버가 허용되어 있는지 확인해야 합니다.
- **허용된 사용 기간 안에 있는가?** 한때 유효했던 토큰도 만료되면 계속 사용할 수 없습니다. 서버는 자격 증명을 사용하는 시점이 허용된 기간에 해당하는지 확인합니다.

서버가 신뢰할 발급자와 허용할 사용 대상은 미리 정한 정책에 따라 결정합니다. 검증에 필요한 정보도 신뢰할 수 있는 경로에서 관리해야 합니다. 위 질문은 검증의 목적을 설명한 것이며, 실제 검사 항목과 방법은 선택한 인증 체계와 토큰 형식에 따라 달라집니다.

자격 증명이 없거나 검증을 통과하지 못하면 비즈니스 작업을 시작하기 전에 요청을 거부해야 합니다. 검증할 수 없다는 이유로 익명 호출자에게 기본 매장 권한을 주어서는 안 됩니다. 또한 토큰은 민감한 정보입니다. 유효한 토큰이 탈취되면 악용될 수 있으므로 안전하게 전달·보관하고 일반 로그에 남기지 않아야 합니다.

### 인증과 인가의 역할 구분

토큰 검증을 통해 호출자가 앨리스라는 사실을 확인했다고 해도, 매장 B의 매출 조회 요청이 허용되는지는 아직 판단해야 합니다. 앨리스가 어떤 작업을 할 수 있고 어느 매장의 데이터를 볼 수 있는지는 애플리케이션의 권한 정책에 달려 있습니다.

인증 단계에서 확인한 호출자 정보를 바탕으로, 다음 인가 단계가 작업 권한과 매장 접근 권한을 판단합니다. 이 두 단계를 연결해야 다른 사람이 앨리스를 사칭하는 요청과, 실제 앨리스가 권한 밖의 매장을 요청하는 경우를 각각 적절하게 처리할 수 있습니다.

여기서 설명한 토큰 흐름은 HTTP 서버에 접근할 때의 예제입니다. 표준 입출력으로 로컬 프로세스와 통신하는 stdio 방식은 다른 인증 구성을 사용할 수 있습니다. 전송 방식에 따른 범위는 [MCP 인가 명세][mcp-auth]를 참고하세요. 구체적인 인증 연동 절차는 문서 끝의 선택 심화 자료에서 이어서 살펴볼 수 있습니다.

## 인가: 작업과 매장 접근 권한 판단

인가(Authorization)는 확인된 호출자가 요청한 작업을 해당 데이터에 수행해도 되는지 판단하는 과정입니다. 앨리스의 신원을 확인한 다음에는, 이번 요청이 앨리스에게 허용된 작업과 매장 범위에 들어가는지 확인합니다.

### 작업 권한과 매장 접근 권한

매장 A의 상품을 검색하는 것과 매출을 조회하는 것은 서로 다른 작업입니다. 같은 매장의 데이터를 대상으로 하더라도 작업에 따라 필요한 권한이 다를 수 있습니다. 반대로 매출 조회가 허용되어 있어도 모든 매장의 매출을 볼 수 있는 것은 아닙니다.

다음 사례에서 작업과 매장에 대한 판단을 함께 살펴보겠습니다.

| 확인된 권한 | 요청 | 판단 |
| :--- | :--- | :--- |
| 앨리스에게 매장 A의 매출 조회가 허용됨. | 매장 A의 매출 조회 | 작업과 매장이 모두 허용되므로 진행함. |
| 앨리스에게 매장 A의 매출 조회가 허용됨. | 매장 B의 매출 조회 | 매장 B에 대한 접근 권한이 없으므로 거부함. |
| 직원에게 매장 A의 상품 검색만 허용됨. | 매장 A의 매출 조회 | 매장은 같지만 매출 조회 권한이 없으므로 거부함. |

이때 확인하는 것은 매장에 근무한다는 사실 자체가 아니라 데이터에 대한 접근 권한입니다. 한 매장의 직원에게 일부 작업만 허용할 수도 있고, 지역 관리자에게 여러 매장의 조회를 허용할 수도 있습니다. 매장이 실제로 존재하거나 활성 상태라는 사실도 호출자의 접근 권한을 증명하지는 않습니다.

여러 사용자의 권한을 관리할 때는 상품 검색과 매출 조회 같은 권한을 묶어 '매장 관리자'라는 역할에 부여하고, 사용자에게 그 역할을 지정할 수 있습니다. 이런 관리 방식을 **역할 기반 접근 제어(Role-Based Access Control, RBAC)**라고 합니다. 역할에 어떤 권한을 포함하고 어느 매장에 적용할지는 애플리케이션 정책으로 정해야 합니다. '관리자'라는 이름만으로 모든 매장에 대한 접근이 허용되지는 않습니다.

### 요청 정보와 권한 정보의 구분

서버는 인증 단계에서 확인한 호출자 정보를 기준으로 그 호출자에게 허용된 작업과 매장을 확인합니다. 권한 정보는 애플리케이션이 관리하거나, 권한 판단에 사용하도록 정한 인증 서비스에서 가져올 수 있습니다. 어느 방식이든 서버가 신뢰하는 출처의 정보여야 합니다.

예를 들어 서버가 확인한 앨리스의 권한에는 매장 A만 허용되어 있는데, 요청에는 매장 B가 적혀 있을 수 있습니다. 이때 매장 B는 앨리스가 조회하고 싶은 대상일 뿐입니다. 서버는 요청된 작업과 매장을 확인된 권한에 대조해야 하며, 요청에 적힌 매장 ID를 그대로 허용 범위로 사용해서는 안 됩니다.

클라이언트 화면이나 AI 모델이 어떤 도구와 매장을 선택했더라도 서버의 판단은 필요합니다. 화면의 선택 항목을 제한했더라도 요청을 직접 보낼 수 있기 때문입니다. 접근 허용 여부는 서버에서 같은 기준으로 확인해야 합니다.

### 권한을 확인할 수 없으면 거부

앨리스의 권한 정보가 없거나 권한 조회에 실패했다고 가정해 보겠습니다. 서버는 앨리스의 접근을 허용할 근거를 확보하지 못한 상태입니다. 이때 임의로 매장 A를 기본값으로 선택해 조회를 진행하면, 확인하지 못한 권한을 새로 부여하는 결과가 됩니다.

**기본 거부(Deny by Default)**는 정의된 규칙에 따라 필요한 권한이 확인된 경우에 접근을 허용하는 원칙입니다. 정상적인 사용자를 포함해 모든 요청을 무조건 차단한다는 뜻은 아닙니다. 허용된 작업과 매장 범위가 확인되면 진행하고, 확인되지 않으면 업무 데이터에 접근하도록 허용하지 않는 것입니다. 설정 누락이나 일시적인 조회 실패도 접근 권한을 넓히는 이유가 되어서는 안 됩니다.

### 요청별 권한 확인과 조회 범위 유지

앨리스가 매장 A의 매출을 조회한 뒤 같은 대화에서 매장 B의 매출을 요청할 수 있습니다. 첫 요청이 허용되었다고 두 번째 요청도 허용되는 것은 아닙니다. 서버는 보고서, 검색, 내보내기, 스키마 설명 등 각 요청이 다루는 작업과 데이터에 대해 인가 정책을 적용해야 합니다.

앨리스의 매장 A 요청과 밥(Bob)의 매장 B 요청이 동시에 처리되고, 각각 해당 매장에 대한 조회 권한이 있다고 가정해 보겠습니다. 밥의 요청을 처리하면서 앨리스의 조회 대상까지 매장 B로 바뀌어서는 안 됩니다. 두 사람 모두 인증과 인가를 통과했더라도 요청 간에 정보가 섞이면 잘못된 매장의 데이터를 반환할 수 있습니다.

**요청별 컨텍스트(Request Context)**는 이번 요청의 호출자, 허용된 작업, 승인된 매장 범위를 해당 요청에 연결해 전달하는 정보입니다. 서버 내부의 다음 처리 단계에서도 같은 요청의 정보를 사용해야 합니다. 다른 요청의 정보로 덮어쓰거나 앞선 도구 호출의 선택을 다음 요청의 권한으로 간주해서는 안 됩니다.

요청마다 권한을 판단한다는 것이 매번 새로 로그인하거나 반드시 권한 데이터베이스를 조회하라는 뜻은 아닙니다. 권한 정보를 확인하는 방식과 관계없이 각 요청에 인가 정책이 적용되어야 한다는 뜻입니다. 권한은 변경될 수 있으므로 과거에 허용되었다는 사실을 영구적인 접근 권한으로 취급해서도 안 됩니다. [OWASP 인가 지침][owasp-authorization]은 기본 거부와 요청별 권한 검사를 설명합니다.

마지막으로, 승인한 범위는 실제 데이터 조회에도 적용되어야 합니다. 앨리스에게 매장 A의 조회만 허용했는데 데이터 접근 단계에서 다른 매장의 행까지 반환한다면 인가 판단의 목적을 달성하지 못합니다. 다음 절에서는 데이터베이스의 행 수준 보안(RLS)이 이 범위를 적용하는 데 어떤 역할을 하는지 살펴봅니다.

## 행 수준 보안(RLS)을 통한 테넌트 격리

### 테이블 권한과 행 접근 제한

매출 테이블에 매장 A와 B의 거래를 함께 저장한다고 가정해 보겠습니다. 테이블의 **행(Row)** 하나는 거래 한 건을 나타내며, 각 거래에는 어느 매장의 데이터인지 구분할 정보가 있습니다. 앨리스에게 매장 A의 매출 조회가 허용되었다면, 실제 조회 결과에도 매장 A의 거래만 포함되어야 합니다.

**행 수준 보안(Row-Level Security, RLS)**은 데이터베이스가 행마다 접근 조건을 검사하도록 하는 기능입니다. 여기서는 '이번 조회에 승인된 매장과 거래의 매장이 일치하는 행만 허용한다'는 정책을 예로 듭니다. 이 정책이 조회 계정에 적용되고 승인 범위가 매장 A라면, 결과는 다음과 같습니다.

| 거래 | 데이터가 속한 매장 | 매장 A 범위의 조회에서 |
| :--- | :--- | :--- |
| 거래 101 | 매장 A | 조회할 수 있음. |
| 거래 102 | 매장 B | 조회할 수 없음. |
| 거래 103 | 매장 A | 조회할 수 있음. |

테이블을 읽을 권한과 그 안의 어떤 행을 읽을 수 있는지는 서로 다른 판단입니다. 테이블 조회 권한이 있어도 RLS가 허용하지 않는 행은 조회 결과에 포함되지 않습니다. 반대로 RLS 정책을 만들었다고 테이블 조회 권한까지 생기는 것도 아닙니다. 필요한 작업 권한과 행 접근 조건이 함께 충족되어야 합니다.

### 사용자 정의 설정값에 저장하는 매장 ID

여기서는 MCP 서버가 앨리스와 밥의 요청을 공통 DB 계정으로 처리하는 설계를 예로 듭니다. 데이터베이스가 접속 주체로 보는 것은 MCP 서버의 DB 계정이므로, 그 계정만 보고 이번 요청이 앨리스의 것인지 밥의 것인지 구분할 수는 없습니다. PostgreSQL은 DB 계정의 권한을 역할(Role)로 관리하며, 이 역할은 앞에서 다룬 '매장 관리자' 같은 애플리케이션의 업무 역할과 구분해야 합니다.

이 예제에서는 서버가 권한을 확인한 뒤, 조회할 매장 ID를 PostgreSQL의 사용자 정의 설정값에 저장합니다. 사용자 정의 설정은 애플리케이션이 이름을 정해 사용하는 설정 항목입니다. RLS 정책은 이 설정값을 읽어 각 행의 매장 ID와 비교하도록 구성합니다.

중요한 것은 이 값이 서버의 인가 결과에서 나와야 한다는 점입니다. 앨리스에게 매장 A만 허용되었는데 요청에 적힌 매장 B의 ID를 그대로 설정값에 저장하면, 예시의 RLS 정책은 B의 행을 허용할 수 있습니다. RLS가 매장 ID를 전달받았다는 사실만으로 앨리스의 권한까지 확인한 것은 아닙니다.

따라서 이 설계는 서버가 접근 권한을 확인한 뒤 매장 ID를 전달하고, 호출자가 그 값을 임의로 바꿀 수 없다는 전제에서 작동합니다. 서버는 허용된 쿼리와 데이터 접근 경로를 통제해야 합니다. 호출자에게 임의의 SQL을 실행하거나 사용자 정의 설정값을 직접 바꾸는 권한을 주면 이 전제가 무너집니다.

### 커넥션 재사용 시 이전 설정값의 영향

커넥션 풀은 데이터베이스 연결을 매번 새로 만드는 비용을 줄이기 위해 연결을 보관하고 재사용합니다. 앨리스의 요청이 매장 A를 조회한 뒤 커넥션을 반환하면, 밥의 요청이 같은 커넥션을 빌릴 수 있습니다. 이때 이전 요청에서 설정한 매장 ID가 남아 있으면 밥의 조회에도 잘못 적용될 수 있습니다.

매장 ID를 저장한 설정값이 적용되는 기간은 이번 DB 작업으로 한정해야 합니다. 이를 위해 이 설계에서는 **트랜잭션(Transaction)** 범위의 설정을 사용합니다. 트랜잭션은 DB 작업을 하나의 단위로 묶어 정상 완료 시 확정하고, 실패하면 되돌릴 수 있게 하는 단위입니다. 작업을 되돌리는 것을 롤백(Rollback)이라고 합니다.

데이터 접근 계층은 커넥션을 빌린 뒤 트랜잭션을 시작하고, 같은 커넥션에서 매장 ID를 사용자 정의 설정값에 저장해 조회합니다. 이 설정값은 그 트랜잭션 안에서만 적용되도록 구성합니다. 다음 요청도 인가 결과에 따라 매장 ID를 새로 설정해야 합니다. 풀에 반환할 때 초기화될 것이라는 기대만으로 요청 간 격리를 맡겨서는 안 됩니다.

트랜잭션이 정상 완료되거나 롤백되면, 트랜잭션 범위의 설정은 그 이전 상태로 돌아갑니다. 이는 어떤 과거 설정이든 모두 지워진다는 뜻은 아닙니다. 이전 상태에 이미 매장 A의 ID가 설정되어 있었다면 다시 그 값이 적용될 수 있으므로, 커넥션의 기본 상태에는 특정 요청의 호출자나 매장 정보가 남아 있지 않아야 합니다.

오류나 취소가 발생한 경우에도 기존 작업을 정리한 뒤 커넥션을 반환해야 합니다. 아직 트랜잭션이 끝나지 않은 커넥션을 다음 요청에 빌려주어서는 안 됩니다. 안전하게 재사용할 수 없는 연결은 폐기하여 다른 요청이 미완료 작업의 영향을 받지 않도록 해야 합니다.

### RLS 활성화와 DB 계정 권한

RLS 정책은 보호할 테이블에 구성하고 활성화해야 합니다. 한 테이블에 적용했다고 다른 테이블까지 자동으로 보호되지는 않습니다. RLS의 적용 대상인 계정으로 조회할 때, 테이블에 RLS를 활성화했지만 허용하는 정책이 없으면 읽을 수 있는 행도 없습니다. 반면 정책을 작성해 두기만 하고 RLS를 활성화하지 않았다면 그 행 제한은 적용되지 않습니다.

서비스가 사용하는 DB 계정에는 필요한 작업 권한만 부여해야 합니다. 매출을 읽는 기능만 제공한다면 데이터를 수정하거나 삭제하는 권한까지 줄 이유는 없습니다. 또한 전체 관리 권한을 가진 슈퍼유저나 RLS 우회 권한이 있는 계정은 행 제한을 우회하며, 테이블 소유자도 기본적으로 RLS의 적용을 받지 않습니다. 서비스의 조회 계정과 테이블을 만들고 관리하는 계정을 구분하는 이유입니다.

검증도 서비스가 실제로 사용하는 제한된 DB 계정으로 수행해야 합니다. 관리자 계정에서 실행한 조회 결과만으로는 서비스 계정에 의도한 행 제한이 적용되는지 알 수 없습니다. 매장 A와 B의 데이터를 준비하고, 각 승인 범위에서 허용된 행만 반환되는지 확인해야 합니다.

매장 ID를 저장하지 않았거나 설정값이 유효하지 않을 때의 동작도 명확해야 합니다. 애플리케이션과 정책은 작업을 중단하거나 보호 대상 행을 조회할 수 없도록 설계해야 합니다. 임의의 기본 매장을 선택하거나 전체 매장으로 범위를 넓히면, 인가 단계에서 확인하지 못한 접근을 DB 단계에서 허용하게 됩니다.

### 집계와 검색 결과의 접근 제한

매출을 합산하거나 주문 상세를 함께 조회하더라도 승인된 매장 범위는 유지되어야 합니다. 개별 거래를 숨겼더라도 다른 매장의 거래를 합계에 포함하면 비공개 정보를 드러낼 수 있습니다. 주문 상세가 다른 매장의 주문에 잘못 연결되지 않도록 데이터의 소유 관계도 일관되게 관리해야 합니다. RLS가 잘못된 데이터 관계까지 자동으로 바로잡아 주지는 않습니다.

공유 상품 설명과 매장별 비공개 재고를 함께 조회하는 경우도 마찬가지입니다. 설명을 여러 매장에서 공유한다는 이유로 다른 매장의 재고까지 반환해서는 안 됩니다. 어느 정보를 누구에게 공유할지는 데이터의 접근 정책으로 정해야 합니다.

비공개 데이터를 바탕으로 만든 임베딩이나 검색 결과 역시 원본의 접근 제한을 보존해야 합니다. 원본 테이블에 RLS를 적용했다는 사실만으로 별도로 저장된 검색 데이터나 이미 만들어진 응답까지 자동으로 보호되는 것은 아닙니다. 데이터가 저장·조회·반환되는 각 경로에서 승인된 범위가 유지되어야 합니다.

## 시스템 전반의 심층 방어

인증, 인가, RLS는 각각 신원, 작업 권한, 데이터 행 접근을 확인합니다. 그러나 올바른 권한을 가진 요청도 서버에 부담을 줄 수 있고, 안전하게 조회한 결과도 전송 중에 노출될 수 있습니다. 접근 권한을 확인하는 것과 함께 입력값, 통신, 자격 증명, 공유 자원을 보호해야 하는 이유입니다.

**심층 방어(Defense in Depth)**는 서로 보완하는 여러 방어 수단을 함께 적용하는 보안 전략입니다. 예를 들어 애플리케이션은 호출자의 작업 권한과 매장 접근 권한을 확인하고, 데이터 접근 계층은 허용된 쿼리만 실행하며, 데이터베이스는 RLS 정책으로 접근 가능한 행을 제한합니다. 각 방어 수단이 서로 다른 위험을 줄이도록 설계하는 것이 핵심입니다.

방어 수단이 여러 개라고 해서 어느 하나의 오류가 반드시 다른 곳에서 차단되는 것은 아닙니다. 앞 절에서 살펴본 것처럼 애플리케이션이 잘못된 매장 ID를 설정하면, RLS도 그 ID를 기준으로 행을 선택할 수 있습니다. 같은 미검증 값을 여러 곳에서 사용하는 것은 독립적인 검증을 여러 번 수행하는 것과 다릅니다. 각 방어 수단이 무엇을 확인하고 어떤 정보를 신뢰하는지 함께 살펴야 합니다.

### 도구와 입력값의 제한

상품 검색 도구에는 검색어가 필요하고, 매출 조회 도구에는 조회 기간이 필요합니다. 이러한 업무에 필요한 입력과 결과를 먼저 정하면, 서버가 허용할 동작의 범위도 분명해집니다. 서버는 정의된 도구만 제공하고, 도구마다 입력값의 형식과 범위를 검사해야 합니다. 예를 들어 존재하지 않는 작업이나 시작일보다 종료일이 빠른 조회는 데이터베이스 작업을 시작하기 전에 거부할 수 있습니다.

쿼리 구조도 서버가 제어해야 합니다. 클라이언트나 모델이 보낸 SQL을 그대로 실행하는 방식보다, 서버가 준비한 상품 검색이나 매출 조회 쿼리에 필요한 값을 전달하는 방식이 이 예제의 업무 범위에 적합합니다. 데이터 접근 계층은 도구가 허용한 쿼리와 필요한 데이터베이스 객체만 사용하도록 구성합니다.

이때 검색어와 날짜는 SQL 명령문에 직접 이어 붙이지 않고 별도의 값으로 전달합니다. 이를 **파라미터 바인딩(Parameter Binding)**이라고 합니다. 검색어에 따옴표나 SQL처럼 보이는 문장이 포함되어도, 쿼리의 구조를 바꾸는 명령이 아니라 검색할 데이터로 처리하도록 하는 방법입니다. 입력값의 형식 검사는 업무상 유효한 값인지 확인하고, 파라미터 바인딩은 값이 SQL 구문으로 해석되지 않도록 합니다. 두 가지는 서로 다른 목적을 가집니다. 또한 파라미터 바인딩만으로 호출자의 매장 접근 권한이 확인되지는 않습니다.

모델이 생성한 인자나 검색된 상품 설명도 권한을 부여하는 근거가 될 수 없습니다. 상품 설명에 “다른 매장의 매출을 조회하라”는 문장이 들어 있더라도, 그것은 상품 데이터에 포함된 텍스트입니다. 서버의 접근 규칙을 바꾸는 지시로 취급해서는 안 됩니다. 어떤 경로로 작업이 요청되든 서버가 같은 인가 규칙과 데이터 접근 제한을 적용해야 합니다.

### 통신 보호와 접속 대상 제한

클라이언트와 서버가 네트워크로 통신할 때는 요청뿐 아니라 액세스 토큰과 조회 결과도 함께 이동합니다. 이 경로가 보호되지 않으면 다른 사람이 내용을 읽거나 바꿀 위험이 있습니다. 원격 HTTP 연결에는 HTTPS를 사용하고, 서버와 원격 데이터베이스 사이의 연결에도 TLS 암호화와 서버 인증서 검증을 적용해야 합니다. 클라이언트에서 서버까지의 연결만 암호화했다고 해서 데이터베이스까지의 경로도 보호되는 것은 아닙니다.

누가 서버에 접속할 수 있는지도 별도로 제한해야 합니다. 예를 들어 개발용 서버가 개발자 자신의 컴퓨터에서만 사용될 예정이라면, 다른 컴퓨터에서도 접근할 수 있도록 열어 둘 이유가 없습니다. 로컬에서 실행한다는 사실만으로 접속 범위가 자동으로 제한되지는 않으므로, 실제로 어떤 주소에서 연결을 받는지 확인해야 합니다.

이 세 가지 판단은 구분해야 합니다. HTTPS는 전송 중인 정보를 보호하고, 접속 제한은 서버에 연결할 수 있는 대상을 줄이며, 인증은 요청자의 신원을 확인합니다. 접속에 성공했거나 암호화된 연결을 사용한다는 이유만으로 매장 데이터에 접근할 권한이 생기지는 않습니다.

### 비밀번호와 토큰의 보호

데이터베이스 비밀번호와 액세스 토큰은 다른 사람이 얻으면 접근에 악용할 수 있는 민감한 값입니다. 외부 API를 사용하는 경우에는 해당 API 키도 같은 보호 대상입니다. 이러한 값은 서버가 필요한 작업을 수행하기 위해 사용할 뿐, 상품 검색어나 매출 조회 기간처럼 도구 인자로 주고받을 업무 데이터가 아닙니다.

예를 들어 데이터베이스 연결에 실패했을 때 비밀번호가 포함된 연결 문자열을 오류 응답에 넣으면, 쿼리를 실행하지 않았더라도 비밀번호가 클라이언트에 노출됩니다. 같은 문자열을 일반 로그에 남기면 로그를 읽을 수 있는 사람에게도 접근 수단을 넘겨줄 수 있습니다. 소스 코드와 버전 관리 기록, 도구 인자, 도구 응답, 오류 메시지, 일반 로그에 이러한 민감한 값이 남지 않도록 해야 합니다.

서버에는 필요한 자격 증명만 제공하고, 이를 읽을 수 있는 사람과 프로그램도 제한해야 합니다. 노출된 자격 증명은 로그에서 가리는 것만으로 해결되지 않으므로, 더 이상 사용할 수 없도록 폐기하거나 교체해야 합니다. 모든 설정값이 비밀인 것은 아닙니다. 공개 키처럼 검증을 위해 공개하는 정보와 비밀번호·토큰처럼 접근에 악용될 수 있는 값을 구분하여 보호 대상을 정해야 합니다.

서버가 다른 서비스를 호출할 때도 자격 증명의 사용 목적을 구분해야 합니다. 호출자가 MCP 서버에 제시한 액세스 토큰을 다른 서비스에서도 사용할 수 있다고 가정하고 그대로 전달해서는 안 됩니다. 다른 서비스의 호출에는 그 서비스에서 인정하는, 필요한 작업에 맞는 권한을 가진 자격 증명이 필요합니다. MCP 서버에서 확인한 매장 접근 권한도 다른 서비스에 자동으로 적용되는 것은 아닙니다.

### 공유 자원의 사용량 제한

앨리스에게 상품 검색 권한이 있더라도, 아주 긴 검색문을 반복해서 보내거나 많은 검색을 동시에 실행하면 문제가 생길 수 있습니다. 로컬 임베딩 모델과 데이터베이스 커넥션은 여러 요청이 함께 사용하는 자원이기 때문입니다. 앨리스의 작업이 이 자원을 모두 차지하면, 밥의 정상적인 요청도 처리되지 못합니다. 접근 권한의 문제와 별개로 서비스가 계속 응답할 수 있는지를 보호해야 합니다.

따라서 요청 하나가 사용할 수 있는 입력 크기, 반환 결과 수, 실행 시간을 제한해야 합니다. 동시에 실행할 쿼리나 임베딩 추론의 수와 대기 중인 요청의 수도 제한할 필요가 있습니다. 실행 중인 작업만 제한하고 대기 요청을 무한히 쌓으면, 대기열 자체가 메모리를 소모할 수 있습니다.

전체 서버의 사용량 제한과 호출자별 또는 매장별 제한은 목적이 다릅니다. 전체 제한은 서버 용량을 넘지 않도록 하고, 호출자별·매장별 제한은 한쪽이 공유 용량을 독점할 가능성을 줄입니다. 접속 지점에서 요청 횟수만 제한하는 것으로는 부족할 수 있습니다. 짧은 조회 한 번과 오래 걸리는 임베딩 검색 한 번이 소비하는 자원이 다르므로, 서버 내부에서 실제로 실행하거나 기다리는 작업량도 관리해야 합니다.

타임아웃이나 취소가 발생했을 때도 실제 작업의 상태를 확인해야 합니다. 데이터베이스 커넥션은 실행 중인 작업과 트랜잭션을 안전하게 정리한 뒤 풀에 반환해야 하며, 안전한 상태로 되돌릴 수 없다면 재사용해서는 안 됩니다. 로컬 임베딩 추론은 요청의 대기가 끝난 뒤에도 계속 실행될 수 있습니다. 이 경우에는 추론이 실제로 끝날 때까지 자원을 사용 중인 작업으로 계산해야 합니다. 응답을 중단했다는 이유만으로 실행 여유가 생겼다고 판단하면, 새 작업이 겹쳐 자원을 고갈시킬 수 있습니다.

이러한 제한은 여러 사용자가 서비스를 계속 이용할 수 있도록 하는 방어 수단입니다. 요청이 정해진 사용량 안에 들어온다고 해서 접근 권한까지 확인된 것은 아니므로, 인증·인가·RLS와 함께 적용해야 합니다.

## 감사 로깅 및 보안 모니터링 (Audit Logging and Security Monitoring)

앨리스가 접근 권한이 없는 매장 B의 매출을 요청했고, 서버가 이를 거부했다고 가정해 보겠습니다. 인가는 이번 요청을 차단했습니다. 그러나 나중에 관리자가 이 일을 조사하려면 누가 어떤 작업을 요청했고, 서버가 왜 거부했는지 알 수 있어야 합니다. 같은 요청이 반복되고 있는지도 확인할 필요가 있습니다.

**감사 로깅(Audit Logging)**은 접근 시도, 권한 판단, 중요한 작업의 처리 결과를 나중에 확인할 수 있도록 기록하는 것입니다. **보안 모니터링(Security Monitoring)**은 이러한 기록과 다른 보안 신호를 살펴보고, 조사나 대응이 필요한 상황을 찾는 활동입니다. 인가가 현재 요청의 허용 여부를 결정한다면, 감사 기록과 모니터링은 그 결정과 이후 상황을 확인하는 데 도움을 줍니다.

운영 로그와 감사 기록은 사용하는 목적이 다릅니다. 예를 들어 데이터베이스 연결 오류를 기록하면 장애 원인을 찾는 데 도움이 되고, 매출 조회가 허용되거나 거부된 사실을 기록하면 접근이 적절했는지 조사하는 데 도움이 됩니다. 목적에 따라 필요한 정보와 보호 수준을 정해야 하며, 반드시 서로 다른 파일이나 저장소를 사용해야 한다는 뜻은 아닙니다.

### 접근 시도와 처리 결과의 기록

앨리스의 요청에 대해 “접근 거부”라는 문장만 남기면 어떤 일이 있었는지 알기 어렵습니다. 다음은 인증으로 앨리스의 신원이 확인된 뒤 매장 B에 대한 접근을 거부한 경우의 기록 예시입니다.

| 항목 | 예시 |
| :--- | :--- |
| 발생 시각 | 해당 요청을 거부한 시각 |
| 인증으로 확인한 호출자 | 앨리스 |
| 요청한 작업 | 매출 조회 |
| 요청한 매장 | 매장 B |
| 처리 결과 | 거부 |
| 이유 | 매장 접근 권한 없음 |
| 요청을 연결하는 식별자 | 이 요청에 부여한 고유한 식별자 |

여기서 매장 B는 앨리스가 요청한 대상입니다. 앨리스에게 접근이 허용된 매장을 뜻하지 않습니다. 요청한 대상과 서버가 확인한 권한 정보를 구분해야, 나중에 기록을 읽는 사람이 거부 이유를 올바르게 이해할 수 있습니다.

하나의 요청에서도 인증, 인가, 데이터 조회 과정에서 여러 기록이 생길 수 있습니다. 이 기록들에 같은 요청 식별자를 남기면 발생 시각이 비슷한 다른 요청과 혼동하지 않고 처리 흐름을 연결할 수 있습니다. 이처럼 관련 기록을 연결하기 위한 식별자를 **상관관계 ID(Correlation ID)**라고 합니다. 식별자는 기록을 연결하는 수단이며, 그 자체가 호출자의 신원이나 권한을 보증하지는 않습니다.

호출자를 기록할 때는 인증으로 확인한 정보와 요청자가 주장한 정보를 구분해야 합니다. 인증에 실패한 요청이 자신을 앨리스라고 주장하더라도, “앨리스가 매장 B에 접근했다”고 확정해서 기록해서는 안 됩니다. 확인할 수 없는 신원은 확인되지 않은 상태로 남기고, 인증에 실패했다는 결과를 기록해야 합니다.

기록할 사건의 범위도 정해야 합니다. 인증 실패와 인가 거부 외에도 성공한 민감 데이터 조회, 접근 권한 변경, 관리 작업은 조사에 중요한 정보가 될 수 있습니다. 어떤 사건을 어느 정도로 남길지는 보호 대상 데이터와 조사 목적에 맞춰 정합니다. 또한 “매출 조회 요청을 받음”, “접근을 허용함”, “조회가 완료됨”은 서로 다른 사실입니다. 요청을 받거나 허용했다는 기록만으로 작업이 성공했다고 판단해서는 안 됩니다.

### 기록할 정보와 제외할 정보

기록은 많을수록 좋은 것이 아닙니다. 매출 조회가 있었음을 확인하려고 매출 내역 전체를 복사해 두면, 감사 기록이 민감한 업무 데이터를 노출하는 또 하나의 경로가 됩니다. 조사에 필요한 호출자·작업·대상·결과를 중심으로 기록하고, 액세스 토큰, 비밀번호, 불필요한 개인정보와 비공개 조회 결과는 그대로 남기지 않아야 합니다.

기록하는 정보의 출처도 중요합니다. 앨리스와 밥의 요청이 같은 서비스 DB 계정으로 실행된다면, 데이터베이스에 그 계정 이름만 남아 있어서는 실제로 누가 요청했는지 구분할 수 없습니다. 서버는 인증으로 확인한 호출자 정보와 요청 식별자를 필요한 감사 기록에 연결해야 합니다. 데이터베이스 접속 계정이나 접속 주소를 최종 사용자의 신원으로 간주해서는 안 됩니다.

외부에서 받은 텍스트가 기록의 의미를 바꾸지 않도록 하는 것도 필요합니다. 예를 들어 입력값에 줄바꿈과 가짜 성공 메시지가 포함되어 있을 때, 이를 그대로 이어 붙이면 별도의 정상 기록처럼 보일 수 있습니다. 이를 **로그 주입(Log Injection)**이라고 합니다. 외부 입력을 기록할 때는 정해진 항목의 값으로 안전하게 처리하여, 다른 사건을 꾸미거나 기존 결과를 왜곡하지 못하도록 해야 합니다.

### 감사 기록의 보존과 접근 제한

실패한 작업을 조사하려면 실패 기록도 남아 있어야 합니다. 그러나 업무 변경과 감사 기록을 같은 데이터베이스 트랜잭션에 저장하면, 작업 실패로 트랜잭션을 롤백할 때 감사 기록도 함께 취소될 수 있습니다. 따라서 보존해야 하는 실패 기록은 업무 트랜잭션이 취소되어도 남길 수 있는 별도의 기록 경로가 필요합니다. 기록을 남기려고 업무 트랜잭션의 실패한 변경까지 확정해서는 안 됩니다.

앨리스의 요청처럼 인가 단계에서 거부된 경우에는 업무 데이터 조회가 아예 실행되지 않습니다. 데이터베이스에서 일어난 작업만 기록하는 방식으로는 이 거부를 알 수 없습니다. 요청을 거부한 서버에서도 필요한 사건을 기록해야 하는 이유입니다. 이후 데이터 변경 기능을 제공한다면 변경을 시도한 사실과 실제로 변경이 확정된 사실도 구분해서 남겨야 합니다.

감사 기록은 접근을 조사하는 자료이면서 그 자체로 보호 대상입니다. 매장 A의 매출을 읽을 수 있다는 이유만으로 다른 직원의 접근 이력이나 다른 매장에 대한 요청 기록까지 읽을 수 있어서는 안 됩니다. 기록을 추가하는 권한과 읽기·수정·삭제 권한을 구분하고, 각 역할에 필요한 권한만 부여해야 합니다. 기록을 전송하고 저장하는 경로도 보호해야 합니다. 테이블을 만들었다는 사실만으로 누락이나 변조가 방지되지는 않습니다.

기록 저장에 실패했는데도 아무도 알아차리지 못하면, 관리자는 기록이 누락된 기간의 접근 시도를 확인하기 어렵습니다. 기록 수집이 중단되거나 지연되는 상황을 발견하고 조치할 수 있어야 합니다. 기록이 없다는 사실만으로 접근 시도가 없었다고 단정해서는 안 됩니다.

기록을 얼마나 오래 보관하고 언제 안전하게 폐기할지도 정해야 합니다. 필요한 보존 기간은 조사 목적과 적용되는 요구사항에 따라 달라집니다. 감사 기록은 규정 준수에 필요한 자료가 될 수 있지만, 기록을 남기는 것만으로 관련 요구사항을 모두 충족하는 것은 아닙니다. 이 실습에서는 모든 시스템에 공통으로 적용할 보존 기간이나 특정 인증 기준을 정하지 않습니다.

### 이상 징후의 해석과 대응

앨리스가 매장 B에 한 번 접근하려 한 것은 매장 선택 실수일 수 있습니다. 반면 짧은 시간 동안 접근 권한이 없는 여러 매장에 반복해서 요청한다면 추가 확인이 필요할 수 있습니다. 보안 모니터링은 개별 기록을 모아 이러한 반복이나 변화를 찾아내는 데 도움을 줍니다. 하지만 의심스러운 신호만으로 공격이라고 확정할 수는 없습니다.

정상적인 행동이 의심스러운 것으로 분류되는 것을 **오탐(False Positive)**이라고 합니다. 예를 들어 여러 매장의 조회 권한을 가진 지역 관리자는 업무 중 여러 매장에 접근할 수 있습니다. 요청 횟수뿐 아니라 실제 접근 권한, 거부 이유, 평소 업무와의 차이 등을 함께 고려해야 합니다. 모든 실패를 같은 중요도로 알리면 중요한 사건이 많은 알림에 묻힐 수 있으므로, 어떤 상황에서 확인이 필요한지 기준을 정해야 합니다.

알림은 보낼 대상과 확인할 내용을 함께 정해야 의미가 있습니다. 예를 들어 반복된 인가 거부를 받은 담당자는 관련 요청 기록을 연결해 보고, 권한 설정 오류인지 잘못된 클라이언트 동작인지 악의적인 시도인지 조사할 수 있어야 합니다. 기록을 일정한 간격으로 확인하는 방식이라면, 사건이 발생한 시점과 발견되는 시점 사이에 지연이 있다는 점도 고려해야 합니다.

모니터링이 정상적으로 작동하는지도 확인해야 합니다. 기록 수집이나 알림 전달이 멈췄다면 이상 징후를 놓칠 수 있기 때문입니다. 또한 알림이 발생하지 않았다는 이유로 요청을 신뢰해서는 안 됩니다. 모니터링은 조사와 대응을 지원하며, 각 요청에 적용하는 인증·인가·RLS를 대신하지 않습니다.

## 보안 경계 검증

인증이나 RLS를 설정했다는 사실만으로 접근 제한이 올바르게 작동한다고 판단할 수는 없습니다. 실제로 요청을 보냈을 때 필요한 접근은 허용되고, 허용되지 않은 접근은 차단되는지 확인해야 합니다. 여기서 말하는 검증은 앞 절의 입력값 검사나 토큰 검증과 달리, 설계한 보안 규칙이 실제 동작으로 이어지는지 확인하는 활동입니다.

검증을 시작할 때는 어떤 상황을 만들고 무엇을 확인할지 먼저 정합니다. 이처럼 조건과 요청, 예상 결과를 정리한 것을 검증 시나리오라고 합니다. 앨리스의 매장 B 접근 요청을 다음 네 요소로 나누어 볼 수 있습니다.

| 요소 | 매장 B 접근 요청의 예 |
| :--- | :--- |
| 호출자의 권한 | 앨리스는 매장 A의 매출 조회 권한을 가지며, 매장 B의 접근 권한은 없음 |
| 요청 | 인증된 앨리스가 실제로 존재하는 매장 B의 매출 조회를 요청함 |
| 예상 결과 | 매장 접근 권한이 없으므로 요청을 거부함 |
| 확인할 내용 | 인가 단계에서 거부되어 업무 조회가 실행되지 않고, 매장 B의 데이터가 노출되지 않으며, 필요한 거부 기록이 남는지 확인함 |

예상 결과는 실행 전에 접근 규칙을 기준으로 정해야 합니다. 실행된 결과를 보고 그대로 정답으로 삼으면 잘못된 동작을 발견할 수 없습니다. 또한 사용자에게 보이는 응답뿐 아니라, 업무 조회가 실행되었는지와 어떤 감사 기록이 남았는지도 필요한 범위에서 함께 확인해야 합니다.

### 허용되는 요청과 거부되는 요청

접근이 거부되는 사례만으로는 충분하지 않습니다. 모든 요청을 거부하는 서버도 권한 없는 요청을 차단할 수 있기 때문입니다. 같은 기능에 대해 허용되어야 할 요청과 거부되어야 할 요청을 함께 확인해야 합니다.

| 시나리오 | 예상 결과와 확인할 내용 |
| :--- | :--- |
| 앨리스가 매장 A의 매출을 요청함 | 작업이 성공하고 매장 A의 허용된 매출 기록만 반환됨 |
| 앨리스가 접근 권한이 없는 매장 B의 매출을 요청함 | 매장 접근 권한 검사에서 거부되며, 매장 B의 매출 조회가 실행되지 않음 |
| 매장 A의 상품 검색만 허용된 직원이 같은 매장의 매출을 요청함 | 매장은 허용되어도 매출 조회 작업 권한이 없으므로 거부됨 |

두 번째와 세 번째 사례는 거부 이유가 다릅니다. 하나는 매장 접근 권한을, 다른 하나는 작업 권한을 확인합니다. 매장 B 요청이 단순히 데이터베이스 장애로 실패했다면 매장 접근 제한이 작동했다고 볼 수 없습니다. 오류 응답의 유무만 보지 말고, 어느 단계에서 어떤 이유로 거부되었는지 확인해야 합니다.

인증도 같은 방식으로 확인합니다. 정상적인 자격 증명은 받아들여지고, 자격 증명이 없거나 변조·만료되었거나 신뢰하지 않는 곳에서 발급되었거나 다른 API용인 경우에는 업무 처리를 시작하기 전에 거부되어야 합니다. 실제로 사용하는 인증 검증 기능이 이러한 차이를 구분하는지 확인해야 하며, 미리 정해 둔 거부 응답을 반환하는 것만으로 토큰 검증이 올바르다고 판단해서는 안 됩니다.

호출자의 작업 권한이나 매장 접근 권한을 확인할 수 없는 상황도 포함해야 합니다. 이때 임의의 기본 매장이나 더 넓은 권한을 부여하지 않는지 확인합니다. 또한 이전에 허용된 요청을 다시 보내더라도, 그 사이 매장 접근 권한이 취소되었다면 적용되는 권한 규칙에 따라 거부되어야 합니다. 과거의 성공이 계속 접근할 수 있는 권한을 뜻하지는 않습니다.

### 반환 데이터와 요청 간 격리

허용된 요청은 성공 여부뿐 아니라 반환 데이터의 소속도 확인해야 합니다. 예를 들어 매장 A에 매출 기록 A-101과 A-102를, 매장 B에 B-201과 B-202를 준비했다고 가정해 보겠습니다. 매장 A 조회에서 두 건이 반환되더라도 그것이 B-201과 B-202라면 데이터 격리는 실패한 것입니다. 반환 건수만 확인하면 이 오류를 놓칠 수 있습니다.

따라서 검증용 데이터는 어느 매장의 기록인지 구별할 수 있도록 준비하고, 반환된 기록의 매장 ID와 개별 기록 식별자를 확인합니다. 필요한 기록이 빠지지 않았는지와 허용되지 않은 기록이 섞이지 않았는지를 함께 살펴야 합니다.

커넥션 재사용은 하나의 요청이 아니라 요청의 순서로 확인합니다.

1. 매장 A에 권한이 있는 앨리스의 요청을 처리하고 커넥션을 풀에 반환합니다.
2. 매장 B에 권한이 있는 밥의 요청이 같은 커넥션을 사용하도록 합니다.
3. 밥의 요청이 자신의 인가 결과에 따라 매장 ID를 설정하고, 매장 A의 데이터나 이전 설정값의 영향을 받지 않는지 확인합니다.

두 요청을 동시에 처리하는 상황에서도 각 요청의 매장 ID와 결과가 섞이지 않아야 합니다. 앞 요청이 정상 종료한 경우뿐 아니라 오류나 취소로 끝난 경우에도 다음 요청의 격리가 유지되는지 확인해야 합니다.

같은 원칙은 보고서, 검색, 여러 테이블을 함께 조회하는 작업과 캐시에도 적용됩니다. 예를 들어 매장 A의 보고서를 캐시에 저장한 뒤 매장 B의 사용자가 같은 종류의 보고서를 요청했을 때, 매장 A의 결과가 반환되어서는 안 됩니다. 여러 매장의 조회 자체가 잘못된 것은 아닙니다. 호출자에게 실제로 허용된 데이터만 반환되는지가 판단 기준입니다.

### 개별 보안 통제와 전체 요청 흐름

각 보안 통제를 따로 확인하는 것과, 서로 연결된 전체 요청 흐름을 확인하는 것은 목적이 다릅니다. 인가는 호출자에게 어떤 작업과 매장 접근을 허용할지 판단하고, RLS는 데이터베이스에 전달된 조건을 기준으로 행을 제한합니다. 각각의 동작을 확인한 뒤, 두 과정이 올바르게 연결되는지도 확인해야 합니다.

RLS 검증은 실제 PostgreSQL에서 서비스가 사용하는 DB 계정으로 수행해야 합니다. 관리자나 테이블 소유자는 RLS 적용에서 예외가 될 수 있으므로, 그러한 계정으로 확인한 결과만으로 서비스 계정의 접근 제한을 판단할 수 없습니다. 권한이 제한된 서비스 계정으로 허용된 행이 조회되고 다른 매장의 행은 조회되지 않는지 확인해야 합니다.

매장 ID를 저장하는 사용자 정의 설정값이 없거나 유효하지 않은 경우도 확인합니다. 이 예제에서는 해당 상태에서 보호 대상 데이터에 접근하지 못하고, 작업이 중단되거나 조회 결과가 없어야 합니다. 이는 이 예제의 설정과 RLS 정책이 충족해야 할 조건입니다. PostgreSQL이 애플리케이션의 매장 ID 의미를 알고 자동으로 이 조건을 보장하는 것은 아닙니다.

이후에는 인증된 요청이 인가를 거쳐 올바른 매장 ID로 조회하고 결과를 반환하는 전체 흐름을 확인합니다. 예를 들어 RLS가 매장 B의 행만 정확히 반환하더라도, 매장 A에만 권한이 있는 앨리스의 요청에 서버가 매장 B의 ID를 설정했다면 전체 흐름은 잘못된 것입니다. 데이터베이스의 행 제한과 서버의 매장 선택이 모두 올바른지 확인해야 합니다.

도구의 입력 처리도 이 흐름에 포함됩니다. 검색어에 SQL처럼 보이는 텍스트가 들어 있더라도 쿼리의 구조를 바꾸지 않고 데이터 값으로 처리되는지, 지원하지 않는 작업이나 범위를 벗어난 입력이 업무 처리 전에 거부되는지 확인합니다. 데이터 변경 기능을 제공하는 경우에는 그 기능의 작업 권한과 행 접근 제한에 맞는 시나리오를 추가합니다. 조회만 제공하는 기능에 아직 없는 변경 작업을 가정하여 검증 범위를 넓힐 필요는 없습니다.

### 실패 후 상태와 감사 기록

요청에 오류 응답을 보냈다고 해서 안전한 처리가 끝난 것은 아닙니다. 오류나 취소 후 커넥션과 트랜잭션이 정리되었는지, 다음 요청이 이전 요청의 상태를 이어받지 않는지 확인해야 합니다. 로컬 임베딩 추론처럼 응답 대기가 끝난 뒤에도 실제 실행이 계속될 수 있는 작업은 종료될 때까지 사용량 제한에서 빠지지 않아야 합니다.

공유 자원의 제한은 다른 사용자의 요청과 함께 확인합니다. 한 매장에서 많은 작업을 요청했을 때 정해진 한도를 넘어 작업이나 대기 요청이 쌓이지 않는지, 다른 매장의 정상 요청을 계속 처리할 수 있는지 살펴봅니다. 이때 확인하려는 것은 구체적인 처리 속도 수치보다, 한 요청이나 매장의 작업이 다른 요청의 처리 기회를 모두 차지하지 않도록 설계한 제한이 작동하는지입니다.

응답과 기록의 내용도 확인해야 합니다. 오류 메시지나 로그에 비밀번호·토큰이 노출되지 않고, 거부된 요청에 업무 데이터가 포함되지 않아야 합니다. 감사 기록에서는 인증으로 확인한 호출자와 확인되지 않은 신원을 구분하고, 요청한 매장, 처리 결과, 거부 이유가 올바르게 남는지 확인합니다. 관련 기록을 요청 식별자로 연결할 수 있는지와 조사에 불필요한 민감 정보가 제외되는지도 살펴봅니다.

업무 트랜잭션이 롤백되거나 DB 조회 전에 요청이 거부되어도, 보존하기로 정한 실패·거부 기록은 남아 있어야 합니다. 이 기록이 작업 완료를 잘못 나타내지 않는지도 확인합니다. 별도의 감사 권한이 없는 호출자가 매장 데이터 조회 권한만으로 감사 기록을 읽거나 변경할 수 없어야 합니다.

모니터링은 의심스러운 요청을 발견했을 때 누가 무엇을 확인할지 설명할 수 있는지 살펴봅니다. 기록 수집이나 알림 전달이 중단된 상황을 알아차릴 수 있는지도 검토합니다. 알림이 없다는 사실만으로 요청이 안전했다거나 필요한 기록이 모두 남았다고 판단해서는 안 됩니다.

마지막으로 다음 질문에 자신의 말로 답해 보십시오.

- 앨리스의 매장 B 요청은 어디에서 어떤 이유로 차단되어야 하나요?
- 거부된 요청뿐 아니라 허용된 요청도 함께 확인해야 하는 이유는 무엇인가요?
- 서버가 잘못된 매장 ID를 설정했을 때 RLS 검사만으로 전체 흐름이 안전하다고 할 수 없는 이유는 무엇인가요?
- 실패 기록이 업무 트랜잭션과 함께 사라지면 조사에 어떤 문제가 생기나요?
- 과거에 성공한 요청이라도 권한이 취소된 뒤 다시 확인해야 하는 이유는 무엇인가요?

이 시나리오들은 앞에서 배운 주요 보안 원칙을 확인하기 위한 예시입니다. 모두 예상대로 동작하더라도 모든 보안 문제가 없음을 보장하지는 않습니다. 도구, 데이터 경로, 권한 규칙이 달라지면 그 변화에 맞는 검증 시나리오도 함께 검토해야 합니다.

## 핵심 요약

- **멀티 테넌트 아키텍처**: 이 실습에서는 매장을 테넌트로 모델링합니다. 서비스와 데이터베이스를 공유하더라도 매장별 비공개 데이터에 대한 접근은 각 호출자의 권한에 따라 제한되어야 합니다.
- **인증**: 인증은 자격 증명을 검증하여 호출자의 신원을 확인하는 과정입니다. 토큰 내용을 읽는 것만으로는 신원을 신뢰할 수 없으며, 인증에 성공해도 작업·매장 접근 권한은 별도로 판단해야 합니다.
- **인가**: 인가는 각 요청의 작업 권한과 매장 접근 권한을 함께 판단하며, 확인한 권한은 실제 데이터 조회에도 적용되어야 합니다. 필요한 권한을 확인할 수 없으면 접근을 허용하지 않는 것이 기본 원칙입니다.
- **데이터 격리**: 이 예제의 RLS는 서버가 인가 결과에 따라 전달한 매장 ID를 기준으로 행을 제한하며, 호출자의 권한을 대신 판단하지는 않습니다. 서비스의 DB 계정에 정책이 적용되어야 하며, 매장 ID 설정값이 다른 요청에 영향을 주지 않도록 관리해야 합니다.
- **심층 방어**: 도구와 입력값의 제한, 통신과 자격 증명의 보호, 공유 자원의 사용량 제한은 서로 보완하는 방어 수단입니다. 각 수단의 역할과 한계를 구분하고 인증·인가·RLS와 함께 적용해야 합니다.
- **감사 및 모니터링**: 감사 기록은 접근 시도와 처리 결과의 사실 확인을, 보안 모니터링은 이상 징후의 조사와 대응을 지원합니다. 필요한 실패·거부 기록도 보존하고 기록 자체의 접근 권한을 제한해야 하며, 이상 징후는 맥락을 살펴 판단해야 합니다.
- **검증**: 검증은 호출자의 권한과 요청에 따른 예상 결과를 먼저 정하고, 허용과 거부가 의도한 이유로 이루어지는지 확인하는 과정입니다. 응답의 성공·실패뿐 아니라 반환 데이터의 소속, 전체 요청 흐름, 실패 후 상태와 감사 기록도 확인해야 합니다.
